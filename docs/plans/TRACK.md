## Decisions / deviations

1. **SDK + Validation**: MCP SDK v2 (`@modelcontextprotocol/server`, 2.0.0 exact) + `@modelcontextprotocol/hono` for transport, Zod v4 for runtime validation (schema passed directly as inputSchema)
2. **Transport**: Streamable-HTTP single local server, stateless (sessionIdGenerator undefined), bound to 127.0.0.1, single `/mcp` endpoint, env-var auth (PLANE_API_KEY + PLANE_WORKSPACE_SLUG + optional PLANE_BASE_URL/PORT)
3. **Tool Scope**: exactly 31 core ticket-workflow tools (users/projects/work items/comments/relations/states/labels/members/cycles/modules) — full catalog in `plans/plane-mcp/00-rfc.md`
4. **Rejected alternatives**: stdio-only transport, full 100+ tool scope (mirroring the official Python server), MCP SDK v1 (`@modelcontextprotocol/sdk`) — rationale in `plans/plane-mcp/00-rfc.md` Alternatives section
5. **Architecture laws**: tools are pure functions `(authContext, args) -> result`; one `PlaneClient` class is the sole Plane API boundary; `list_*` tools return the raw pagination envelope (no auto-paging); 429s surfaced as tool errors, never swallowed; field-name asymmetry (`state`/`state_id`, `assignees`/`assignee_ids`, `target_date`/`due_date`) normalized centrally in `src/plane/normalize.ts`
6. **Tooling stack (Phase 02)**: Prettier is the single formatter for every file type (`.ts`, `.json`, `.md`) with per-language overrides — no Biome. oxlint (`.oxlintrc.json`) owns `.ts` correctness/linting, enforcing the three hard-rule mappings: `typescript/consistent-type-definitions` (type-over-interface), `typescript/no-explicit-any`, `typescript/consistent-type-imports`. typescript-eslint was rejected because it lacks TypeScript 7 support; oxlint is a Rust-based linter with zero TypeScript compiler coupling, so the TS7 pin cannot break it. A committed, zero-dependency `.githooks/pre-commit` script (wired via `git config core.hooksPath .githooks`) runs Prettier then oxlint before every commit; `--no-verify` is never used. Phase 02 runs immediately after scaffold, before any feature code, so the one-time full-repo baseline reformat never collides with a later feature commit.
7. **stdio transport added (Phase 11, post-hardening)**: `plans/plane-mcp/00-rfc.md`'s Non-goals originally listed "stdio transport. HTTP-only." This is amended, not reversed: stdio is added as a second, additive transport (`src/stdio.ts`, reusing `createServer()`/`loadAuthContext()` unmodified) for local single-user install via `bun link` and command-launched MCP client configs (`mcpServers.<name>.command`). HTTP (`src/index.ts`) remains the transport for the "one server, multiple clients" shape the RFC locked in and is unchanged by this phase. `package.json` `bin.plane-mcp` now points at the stdio entry (the default local-MCP command); a new `bin["plane-mcp-http"]` covers the HTTP entry explicitly. `private: true` unchanged — no npm publish; `bun link` needs no registry. Full rationale: `plans/plane-mcp/00-rfc.md` Non-goals + Alternatives amendments; full spec: `plans/plane-mcp/11-distribution.md`.
8. **Type-aware linting reclaimed (Phase 12)**: Phase 02 adopted oxlint over the ESLint/`typescript-eslint` stack because `typescript-eslint` has no TypeScript 7 support path, and explicitly recorded type-aware linting as an unavailable capability at that time (oxlint was, at the time, purely syntactic). `typescript-eslint` still has no TS7 support as of this phase (peer range `>=4.8.4 <6.1.0`, latest published `8.66.0`; upstream tracking issue #12518 closed "not planned," pending an unshipped TS7.1 stable compiler API) — so ESLint remains off the table. However, oxlint shipped stable type-aware linting via `tsgolint` on 2026-07-22 — a Go-based rule engine with its own embedded TS7-compatible compiler, independent of the `typescript` npm package/`tsc`, so it is unaffected by the incompatibility blocking `typescript-eslint`. Phase 12 turns this on: `oxlint` bumped to `1.77.0`, new exact-pinned devDep `oxlint-tsgolint@7.0.2001` (prebuilt Go binary via npm `optionalDependencies`, no Go toolchain needed), `.oxlintrc.json` gains root `options.typeAware: true` plus `typescript/no-floating-promises`, `typescript/no-misused-promises`, `typescript/await-thenable` (and `typescript/require-await` per a recorded per-implementation decision) as `"error"`. Config format stays `.oxlintrc.json` (JSON) — `oxlint.config.ts` was rejected because it requires a Node v22.18+/v24+ runtime, which does not work under Bun. No CI workflow change: the existing frozen `bun install` step already resolves `oxlint-tsgolint`'s platform optional dependency once `bun.lock` is regenerated and committed. This reverses the Phase 02/05-era compromise, not the RFC's linter choice — oxlint remains the linter; only its configuration gained a capability. Full spec: `plans/plane-mcp/12-type-aware-lint.md`.

9. **Tool layer depends on `PlaneApi`, not `PlaneClient` (Phase 13)**: `PlaneClient` is a nominal class whose private `auth` field brands the type, preventing structural test stubs from type-checking without casts. Phase 13 eliminated all 20 `as unknown as` double-casts by defining an explicit structural `PlaneApi` type in `types/client.ts` that `PlaneClient` implements; the tool layer (`types/mcp.ts`, `src/tools/register.ts`, all `src/tools/*.ts` files) depends on `PlaneApi`, not the concrete class. Fetch mocks moved from global mutation (`globalThis.fetch = mock as unknown as typeof fetch`) to constructor injection via a `FetchLike` type (also in `types/client.ts`): `PlaneClient` takes an optional `fetchFn: FetchLike` parameter, so tests pass `new PlaneClient(auth, mock<FetchLike>(...))` with no cast. Tool tests use the shared `stubClient()` helper (in `src/tools/client-stub.ts`) whose only casts are the three necessary `as T` generics per method. `WorkItemWriteInput` moved to `types/plane.ts`, `RequestOptions`/`FetchLike` to `types/client.ts`. `typescript/no-unnecessary-type-assertion` oxlint rule added. Full spec: `plans/plane-mcp/13-test-type-safety.md`.

11. **Persistent macOS launchd service with Keychain secrets (Phase 15)**: Phase 15 enables running plane-mcp as a user-scoped LaunchAgent that persists across login sessions. Secrets (PLANE_API_KEY, PLANE_WORKSPACE_SLUG) are stored once in the login Keychain via `security add-generic-password` with the `-T /usr/bin/security` pre-auth flag, preventing repeated prompts on LaunchAgent reads. `scripts/plane-mcp-serve.sh` uses `security find-generic-password` to read secrets and `exec`s `bun run start` (no hardcoded secrets). `scripts/store-secrets.sh` prompts interactively once to capture and store secrets. `scripts/install-launchd.sh` uses `sed` to fill a plist template's `__SERVE_SH__` and `__HOME__` placeholders with portable absolute paths (derived at runtime, not hardcoded), then `launchctl bootstrap/kickstart` to load the agent. `deploy/com.plane-mcp.server.plist` is the template (plist is valid; placeholders are plain strings). `scripts/uninstall-launchd.sh` unloads the agent and removes the plist. All paths are portable (BUN defaults to `$HOME/.bun/bin/bun`; APP_DIR derived from script location; HOME passed to plist). The design targets user-scoped agents (login time, not pre-login boot; LaunchDaemon is out of scope). README documents the 3-step flow (store-secrets → test interactively → install-launchd), Keychain first-read prompt caveat (click Always Allow), log paths (`~/Library/Logs/plane-mcp.*.log`), and uninstall. `.npmignore` already excludes `scripts/` and `deploy/` (not shipped in npm tarball). No hardcoded secrets anywhere. Full spec: `plans/plane-mcp/15-local-service.md`. **Superseded location (Phase 16, 2026-08-07)**: this phase's output was never committed at the repo-root `scripts/`/`deploy/` paths above; Phase 16 relocates and generalizes it to `examples/macos-launchd/` as an optional macOS-only add-on rather than the standard local-setup path — see Decision 12.

12. **Cross-platform keychain-backed multi-instance auth via `plane-mcp init` (Phase 16)**: env-var auth (`PLANE_API_KEY` pasted into the MCP client config) is no longer the only supported setup path. `plane-mcp init <name>` (new `src/cli.ts` dispatcher + `src/cli/init.ts`) prompts once for the API key with hidden input and stores it in a new cross-platform secrets module (`src/secrets.ts`, types in `types/secrets.ts`), namespaced `plane-mcp/<name>`: macOS uses the real Keychain via `security` (`add-generic-password -U` / `find-generic-password -w` / `delete-generic-password`), Linux uses the real Secret Service via `secret-tool` (secret piped on stdin, never argv) when present, and Windows uses a documented file fallback (`~/.config/plane-mcp/credentials`, mode `0600`) because `cmdkey` can write but not read back a Credential Manager secret — a real limitation, not silently worked around. `src/config.ts`'s `loadAuthContext` becomes `async` and gains a resolution order: `PLANE_API_KEY` env (unchanged, CI/dev fallback, checked first) → `PLANE_MCP_INSTANCE`-keyed keychain read → a `plane-mcp init <name>` guidance error. `init` prints a ready-to-paste `mcpServers.plane-<name>` config block containing `PLANE_MCP_INSTANCE`/`PLANE_WORKSPACE_SLUG`/`PLANE_BASE_URL` env vars and **never the API key**; an optional `--register` flag also runs `claude mcp add`. Multiple `init` runs under different names create independent keychain entries and independent MCP server configs with no collision, making multiple named local installs (one per Plane workspace) the supported local-multi-workspace shape — the RFC's "one `PLANE_WORKSPACE_SLUG` per server process" constraint is unchanged (still true per process), only the "one installation" framing is relaxed. `package.json`'s `bin.plane-mcp` becomes a small dispatcher (`init` subcommand vs default stdio passthrough); `bin.plane-mcp-http` and `src/index.ts` are untouched. As part of this phase, the uncommitted Phase 15 macOS launchd artifacts (`scripts/*.sh`, `deploy/com.plane-mcp.server.plist`) are relocated and generalized into `examples/macos-launchd/`, demoted from a root-level default to an optional, explicitly macOS-only, optional persistence add-on; `.npmignore` gains an `examples/` exclusion; README's root-level launchd section is replaced by a pointer to the example plus the new `plane-mcp init` setup flow as primary. Full rationale + Windows caveat + open questions: `plans/plane-mcp/16-secure-setup.md`; RFC amended (Non-goals, AuthContext design, Alternatives) in `plans/plane-mcp/00-rfc.md`, dated 2026-08-07.

13. **Work-item endpoint correctness fix inserted as Phase 18, response-shaping phases resequenced (2026-08-15)**: two confirmed bugs against the public Plane REST API (self-hosted Community) were found while the Phase 17-20 response-shaping work was still in spec form (none implemented yet): (1) `list_work_items`'s array filters (`assignee_ids`, `state_ids`, `state_groups`, `priorities`, `label_ids`, `cycle_ids`, `module_ids`) are silently dropped by Plane's public `/work-items/` list endpoint — only `cursor`, `per_page`, `order_by`, `expand`, `fields`, `external_id`, `external_source` are honored; the call succeeds and returns an unfiltered page with no error signal; (2) `search_work_items`'s `.../work-items/search/` endpoint 404s on Community, since Plane's native search requires a Pro-tier OpenSearch integration. Both bugs predate this feature and are unrelated to response-shaping; both are confirmed against a live instance, not assumed from `docs/plane-api-reference.md` (which documents both as if they worked). A new Phase 18 (`plans/plane-mcp/18-work-item-endpoints.md`) fixes them: `module_ids`/`cycle_ids` become singular `module_id`/`cycle_id` (breaking schema change) routed to Plane's already-confirmed-working per-module/per-cycle work-items sub-endpoints (`src/tools/modules.ts`/`cycles.ts` gain internal, unregistered `fetchModuleWorkItems`/`fetchCycleWorkItems` helpers — the RFC's locked 31-tool scope is unchanged, no new tool is registered); the remaining five filters and all of `search_work_items`'s matching become a bounded client-side scan over the base `/work-items/` endpoint (`src/plane/paginate.ts`'s `scanPages`, capped at `CLIENT_SIDE_SCAN_MAX_ITEMS`/`CLIENT_SIDE_SCAN_MAX_PAGES`, surfaced to the caller via a `truncated` response field, never silently incomplete); `state_groups` filtering resolves each item's group via a new `getProjectStates` helper extracted from `list_states` (`list_states`'s registered behavior is unchanged — pure refactor). This phase deliberately ships raw/unprojected output — Phase 19 (formerly 18, list-projections) now depends on Phase 18 explicitly, because allowlist field projection must run after client-side filtering, never before (projecting away `state_id`/`priority`/`assignee_ids`/`label_ids` before filtering on them would silently break the filter). The original Phase 18-20 response-shaping docs are renumbered to 19-21 with no other design change to Phases 20→19 (retrieve-shaping, unaffected by either bug) and updated cross-references/dependencies for 19 (list-projections, dual envelope-shape handling for `list_work_items`/`search_work_items` added) and 21 (context-docs, scope extended to document Phase 18's client-side filtering/search contract and the scan cap in tool descriptions and `README.md`, plus a new `CLAUDE.md` routing row). The stale `plans/plane-mcp/18-list-projections.md`, `19-retrieve-shaping.md`, `20-context-docs.md` paths now contain redirect stubs pointing at their renumbered files. Full rationale, live-confirmation evidence, and the build-time sub-endpoint verification step: `plans/plane-mcp/18-work-item-endpoints.md`; RFC amended (Proposed design, Phase sketch) in `plans/plane-mcp/00-rfc.md`, dated 2026-08-15.

14. **Configurable per-tool output-token limits, reject-and-guide, config file split from env (Phases 22-25 planned, 2026-08-28)**: a validated, file-based `ServerConfig` is added alongside the existing env-var-only `AuthContext`, deliberately kept separate — `AuthContext` stays secrets/deploy values only (`PLANE_API_KEY`, `PLANE_WORKSPACE_SLUG`, `PLANE_BASE_URL`, `PORT`); `ServerConfig` is behavior/tuning values in a JSON file (v1: `defaults.maxOutputTokens` plus an optional per-tool `tools.<name>.maxOutputTokens` override). Phase 22 adds the type (`types/config.ts`), a Zod v4 `.strict()` schema, `loadServerConfig()`'s discovery order (`PLANE_MCP_CONFIG` absolute path → `./plane-mcp.config.json` → `~/.config/plane-mcp/config.json`, honoring `XDG_CONFIG_HOME`/`PLANE_MCP_CONFIG_DIR` — reusing the same directory `src/secrets.ts` already resolves, now shared via a new `src/paths.ts`) → built-in defaults (zero config required), `resolveMaxOutputTokens`, and a JSON-Schema generator (`z.toJSONSchema()`, no new dependency) producing a committed `plane-mcp.config.schema.json`. Phase 23 adds the actual enforcement: `gpt-tokenizer@4.0.0` (pure-JS, MIT, zero runtime deps, o200k_base/GPT-4o encoding) counts the real outgoing payload (`content` text plus `structuredContent`, since both are sent to the client) with a ×1.2 multiplier (gpt-tokenizer's o200k_base undercounts Claude's actual token usage by roughly 15-20%); `ServerConfig` is threaded through `createServer(auth, config)`, every `registerXTools`, and `toolHandler`, which now discards a breaching result entirely and returns a guidance error (tool name, estimated count, configured limit, concrete narrowing options: `fields`, `per_page`, `module_id`/`cycle_id`, `retrieve_work_item_by_identifier`) — never a truncated payload, never a re-counted already-`isError` result. Phase 23 explicitly flags, without fixing, a pre-existing property of every tool's return statement (Phases 05-09): `content`/`structuredContent` duplicate the same object into the outgoing payload; the token counter must measure that real doubling rather than under-count it, and collapsing the duplication is left to Phases 19-20 (still `[ ]` todo, already touching every tool's return statement) or a later phase. Phase 24 extends `plane-mcp init` with a config-scaffold step (writes a starter file with `$schema` + `defaults.maxOutputTokens`, never overwrites an existing file, never writes the API key into it, records `PLANE_MCP_CONFIG` in the printed MCP client config), a non-interactive `-y` flag, and a new `plane-mcp help`/`--help`/`-h` subcommand. Phase 25 documents all of it in `README.md`, `.env.example`, and `CLAUDE.md`'s routing table (`docs/SECURITY.md`'s `gpt-tokenizer` entry is recorded in Phase 23, at the point the dependency is added, not duplicated in Phase 25). **Recommended build order**: Phase 22 first (pure addition, zero existing call sites touched, can land independently of everything else); Phase 23 next — it changes the signature of `createServer`, every `registerXTools`, and `toolHandler`, the same seam Phases 17/19/20 (response shaping, still `[ ]` todo) converge on from a different angle (return-statement shape, not signature) — so Phase 23 and Phases 17/19/20 should not be implemented concurrently against those files to avoid merge conflicts, though either feature line may go first; Phase 24 depends only on Phase 22's `getConfigDir` and config shape; Phase 25 lands last. Full design: `plans/plane-mcp/22-server-config.md` through `plans/plane-mcp/25-config-docs.md`; RFC amended (Proposed design) in `plans/plane-mcp/00-rfc.md`, dated 2026-08-28.
